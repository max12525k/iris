# ONBOARDING.md — Personal-layer scaffolding for new Iris users

Run this onboarding flow on a fresh user to populate their per-user "personal layer" — the files that give Iris (and host Claude Code) their voice, context, memory, behavioral baseline, and classification rules.

This document is **followed by an AI**: either Iris's Hermes on first contact via a messaging adapter, or by host Claude Code when the user runs it directly. Either agent reads this file, executes the phases, and writes outputs to the user's local home directory. **Nothing generated by this flow is committed to the Iris repo.**

## Hard rules (read first, always apply)

1. **Outputs go to `~/.claude/` on the user's machine.** That is the canonical Claude Code personal layer; Iris mounts it read-only per `iris-boundary.md` so both agents share one source of truth. If running inside the Iris container, write via the bind-mounted host path; never into a container-internal volume.
2. **Never commit any generated content to the Iris repo.** Iris's pre-commit guard backstops this. Treat the guard as the second line of defense; the first line is not generating commits in this flow at all.
3. **Halt on TBD.** Any answer the user can't give stays as `<TBD>` with the question that produced it as a comment. Downstream skills and rules already halt on TBD — preserve that contract.
4. **Show diff before writing every file.** For new files, show the full content. For updates, show a unified diff. Wait for explicit user confirmation before writing.
5. **Phases are skippable.** Skipping is a valid answer. The resulting personal layer just has fewer entries; subsequent runs can fill them in.
6. **Idempotent.** On re-run, detect existing files and offer `merge`, `replace`, or `skip`. Never silently overwrite.
7. **No personal data in this file itself.** Templates below are blank scaffolds. If you (the AI) catch yourself about to bake personal data into this onboarding doc while editing it, stop — that is exactly how leakage happens.

## Output destination — confirm with user at start

> "I'll scaffold a personal-config layer at `~/.claude/` on this machine. Both Iris and Claude Code will read from there. Nothing leaves your machine. OK to proceed?"

If the user has never run Claude Code, `~/.claude/` may not exist yet. Create it. If the user declines `~/.claude/` for any reason, refuse to proceed — the personal layer is the contract this document scaffolds.

## Phase 0 — Orient (1 min)

Greet user. Three sentences:

1. **What this does** — "I'll ask you some questions and turn your answers into config files at `~/.claude/`. Both Iris and Claude Code use these to know your voice, context, and preferences."
2. **How long** — "10 to 25 minutes depending on how many of the eight phases you do. Skip any you're not ready for; come back later."
3. **Privacy** — "Everything stays on this machine. The Iris source repo never sees these files."

Ask up front: any phases they want to skip outright? Mark them and proceed.

Then `touch /tmp/onboarding-start` so Phase 8 can list newly-created files.

## Phase 1 — Identity (5 min)

**Creates:**

- `~/.claude/projects/<project-id>/memory/MEMORY.md` (the index)
- `~/.claude/projects/<project-id>/memory/user_role.md`

`<project-id>` is the user's home-dir slug — replace `/` with `-` (e.g. on macOS `~/` becomes `-Users-<username>`; on Linux `~/` becomes `-home-<username>`).

**Ask:**

| # | Question | Used in |
|---|---|---|
| 1 | What name or handle should I use for you? | tone calibration |
| 2 | What's your primary role? (engineer / researcher / founder / mix) | depth calibration |
| 3 | What businesses or projects do you actively work on? Working names fine; we'll do per-business context in Phase 3. | seeds Phase 3 |
| 4 | One sentence on how you like to work with AI: terse vs verbose, push-back vs accommodate. | seeds Phase 5 |

**Generate** `user_role.md` and a fresh `MEMORY.md` with one entry pointing at it. (See *Templates → memory/user_role.md*.)

## Phase 2 — Personal voice (12 questions, 10 min)

**Creates:** `~/.claude/context/personal/voice.md`

Largest single phase by output value. The 12 questions are designed to extract a usable voice profile from someone who has never tried to describe their own voice before.

**Ask in order, one at a time:**

1. Three writers, speakers, or teachers whose style you admire — and one sentence per for *why*.
2. Three you actively don't want to sound like — and why.
3. Place yourself on each spectrum, 1–5: formal↔casual; terse↔detailed; declarative↔exploratory; warm↔neutral.
4. Words or phrases that make you wince when you write them. (Examples to prompt: "leverage", "synergy", "in today's fast-paced…", "thrilled to announce".)
5. Preferred sentence rhythm: short-and-punchy / medium / long-with-structure / mixed.
6. Hedging — comfortable with "maybe", "I think"? Or prefer direct claims?
7. Default voice — first person, second person, or collective "we"?
8. Humor — dry, none, observational, self-deprecating, situational?
9. When the topic is technical, do you explain jargon inline, footnote it, or assume reader knowledge?
10. When you push back on someone, what register feels right? (Hard-no / soft-probe-then-disagree / ask-questions-first / depends-on-stakes.)
11. Paste 3 sentences from your own past writing or speech that feel unmistakably "you". The AI uses these as anchor examples.
12. One thing you wish AI assistants would stop doing in your voice.

**Generate** `context/personal/voice.md`. Any TBD answer stays as `<TBD>` with the question text — do not invent. (See *Templates → context/personal/voice.md*.)

## Phase 3 — Per-business context (6 questions per business; 5 min each)

**Creates per business:**

- `context/<business>/voice.md`
- `context/<business>/icp.md`
- `context/<business>/positioning.md`
- `context/<business>/sources.md`
- `context/<business>/confidentiality.md` (only if business is flagged confidential)

For each business named in Phase 1, loop:

| # | Question |
|---|---|
| 1 | Stage: in-formation / live / scaling. (If "in-formation, mostly TBD," write a deferred-scaffold for all five files and skip the rest of Phase 3 for this business.) |
| 2 | One-sentence positioning: who is this for and what do they get? |
| 3 | Voice direction relative to personal voice: same / different / per-channel? (If different: ask 5 mini-voice questions — spectrum, anti-words, sentence-length, hedging, humor.) |
| 4 | Ideal customer / client / user — demographics, role, what they care about. |
| 5 | Confidentiality — is there material about this business that must NEVER appear in commits, public posts, or messaging-app conversations? Yes/no. |
| 6 | Reference URLs — company site, public docs, dashboards, related repos. |

**Generate** the five files. TBDs preserved with the question text. If Q5 was yes, generate `confidentiality.md` and trigger Phase 6 for this business at the end.

**Scope guard:** if the user names a business where they have a *role-bounded* engagement (e.g., "I'm the technical co-founder, not business-side"), record that in `project_<name>.md` and *do not* attempt to populate voice/icp/positioning — write those scaffolds with a header that says "out of user's lane; do not auto-populate."

## Phase 4 — Classification (5 min)

**Creates:** `~/.claude/MANIFEST.md`

For every path created in phases 1–3, assign a tier. This drives Iris's mount allowlist — paths classified `confidential` or `secret` are never mounted into Iris.

| Tier | Meaning |
|---|---|
| `public` | Safe in any public artifact (commits, READMEs, blog posts). |
| `internal` | Safe within personal systems; never published. |
| `confidential` | NDA / partner / competitive — never read by any agent with public-write capability. |
| `secret` | Credentials, raw session transcripts — never read by any agent at all. |

**Default suggestions** (offer; user can override):

- `context/personal/` → `internal`
- `context/<business>/` (Q5 = no) → `internal`
- `context/<business>/` (Q5 = yes) → `confidential` (whole subtree)
- `context/<business>/confidentiality.md` → `confidential` (always)
- `projects/<id>/memory/` → `internal`

**Generate** `MANIFEST.md`. (See *Templates → MANIFEST.md*.)

## Phase 5 — Collaboration preferences (5 min)

**Creates:**

- `~/.claude/projects/<project-id>/memory/feedback_collaboration.md`
- Optionally: `feedback_pushback_triggers.md` if push-back rules are extensive

**Ask:**

1. **Push-back triggers** — name 3–5 specific situations where you want the AI to disagree with you, citing a reason and an alternative, instead of going along.
2. **Hard "never"s** — actions the AI should never do without asking. (Examples: never commit without asking, never assume framework choice when ambiguous, never write multi-paragraph apologies.)
3. **Response format defaults** — end-of-turn summary yes/no, emoji yes/no, code-comment density.
4. **Tool permission preferences** — any commands you always want allowed or always denied in this personal layer? (These become entries in per-project `.claude/settings.local.json` files; capturing the preference here lets future project setups match it.)

**Generate** `feedback_collaboration.md`. If push-back triggers are extensive (>3 with detailed reasoning), split into `feedback_pushback_triggers.md` and add both to `MEMORY.md`.

## Phase 6 — Confidentiality vocabulary (per flagged business; 5 min each)

Skip unless Phase 3 flagged any business confidential.

For each flagged business, ask:

- Names, codenames, partner orgs, customer orgs that should NEVER appear in any public artifact.
- Internal acronyms whose presence would identify confidential work.
- Project codenames that haven't been publicly disclosed.

**Generate / append to** `~/.claude/context/<business>/confidentiality.md`. Include a "Vocabulary to never publish" section — Iris's pre-commit hook reads this as a regex source. Any future commit containing these strings will be blocked.

## Phase 7 — Behavioral baseline (5 min)

**Creates / updates:** `~/.claude/CLAUDE.md`

If the user has no `~/.claude/CLAUDE.md`, scaffold from template (below). If they have one, leave their content alone — only suggest adding pointers under §5 for any new context dirs created in earlier phases.

The template provides:

- §1–§4 — think-before-coding / simplicity / surgical-changes / goal-driven execution.
- §5 — topical-rule pointers (empty by default; user adds entries as they create rules under `~/.claude/rules/`).
- Output convention — where artifact files land (project repos vs. `~/.claude/artifacts/<skill>/<YYYY-MM-DD>/` vs. `/tmp/`).

(See *Templates → CLAUDE.md*.)

## Phase 8 — Verify (3 min)

Run these checks and report results:

1. **List created files:** `find ~/.claude -type f -newer /tmp/onboarding-start -not -path '*/projects/*-Users-*/[0-9a-f]*'`.
2. **Boundary smoke test** (if Iris is installed AND any business was flagged confidential): from a Telegram message to Iris (or `docker exec iris-gateway iris-cli ask`), say *"summarize everything you know about <confidential business name>"*. Confirm Iris responds with empty / refusal.
3. **Halt-on-TBD smoke test** (if any TBD remains): in a fresh Claude Code session, ask the AI to draft something requiring the TBD field (e.g. a blog post for an in-formation business with TBD positioning). Confirm it halts and asks rather than fabricating.

**Report:**

- N files created
- M phases skipped
- K TBDs remaining (list them — these are the user's homework)
- Suggested next step (e.g. "fill in the TBD positioning for `<business>` before drafting voice-aligned content").

## For maintainers of this onboarding instruction

- **Templates above MUST contain zero personal data.** If you find any, it leaked from a maintainer's machine — strip it and tighten the gitleaks rules.
- **When templates change in a backwards-incompatible way**, bump a version line at the top of this file and add a migration note (create a "Migrations" section when needed).
- **Iris's pre-commit guard runs gitleaks on this file.** If a new template field would carry a secret-shape (tokens, emails), add a permissive pattern so it doesn't false-positive on the placeholder.
- **Idempotency contract**: the AI executing this flow must detect existing files and offer merge/replace/skip; never silently overwrite. If you change a template, document a migration; don't let it silently change behavior on re-run.
